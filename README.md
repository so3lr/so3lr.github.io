# so3lr.github.io

Documentation site for [SO3LR](https://github.com/general-molecular-simulations/so3lr),
built with [MkDocs Material](https://squidfunk.github.io/mkdocs-material/) and
published at **<https://so3lr.github.io/>**. This repository holds the source
and is the only place the docs are edited; the code lives in
[`general-molecular-simulations/so3lr`](https://github.com/general-molecular-simulations/so3lr).

## Local preview

```shell
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
mkdocs serve
```

Open <http://127.0.0.1:8000>. The server live-reloads on save.

## Build

```shell
python scripts/check_snippets.py    # code blocks
mkdocs build --strict               # pages, nav, internal links
python scripts/check_anchors.py     # #anchors (needs site/ from the build)
python scripts/build_llms_full.py   # regenerate site/llms-full.txt
```

CI runs all three on every push, so run them before pushing.

| Check | Catches |
|---|---|
| `check_snippets.py` | Python that does not parse; snippets using a name never defined on the page; `so3lr` CLI flags documented nowhere. Executes nothing — SO3LR is not installed in docs CI. |
| `mkdocs build --strict` | Links to pages that do not exist, bad nav entries. |
| `check_anchors.py` | Links to a **heading** that does not exist. `--strict` misses these: they build fine and 404 in the browser. |

## Machine-readable docs

Two files follow the [llms.txt](https://llmstxt.org/) convention:

| File | Source | What it is |
|---|---|---|
| `/llms.txt` | `docs/llms.txt`, hand-written | Curated index: a summary, the facts assistants most often get wrong, and annotated links to every page. Copied verbatim by mkdocs, so **update it when the nav changes**. |
| `/llms-full.txt` | generated by `scripts/build_llms_full.py` | Every page concatenated in nav order (~139 KB), for pasting into a context window. Regenerated on each CI build. |

The human-facing version of the same material is
`docs/advanced/llm-agents.md`. Repo-modification guidance lives in `AGENTS.md`
and `DEVELOPERS.md` in the code repository instead — different audience.

## Publishing

Every push to `main` runs the checks, builds the site and deploys it with
`.github/workflows/deploy.yml`. **Settings → Pages → Source** must be set to
**GitHub Actions** (one-time setup).

`site_url` in `mkdocs.yml` and the absolute links in `docs/llms.txt` and
`docs/contributing.md` point at `https://so3lr.github.io/`; change all three
together if the URL ever changes.

## Style variants

The active stylesheet is `docs/stylesheets/extra.css`. It is **generated** by
concatenating `styles-preview/_base.css` (structure) with one variant file
(color and type). Swap between them while `mkdocs serve` is running:

```shell
./swap-style.sh scaling      # active — adapted from the JAX scaling book
./swap-style.sh paper        # maximum-minimal, white header + hairlines
./swap-style.sh graphite     # near-black header, warm neutrals, orange accent
./swap-style.sh editorial    # serif headings, printed-table rules, teal
./swap-style.sh current      # the original Material green header
```

Edit the variant in `styles-preview/`, not `docs/stylesheets/extra.css` — the
latter is overwritten on the next swap. Once you have settled on one, you can
delete `styles-preview/` and `swap-style.sh` and keep the generated file.

!!! note
    Material declares `--md-typeset-a-color: var(--md-primary-fg-color)` on
    `<body>`. For an inherited custom property the nearer ancestor wins over a
    `:root` declaration regardless of specificity, so variants set
    `--so3lr-link` and `_base.css` re-asserts it at `[data-md-color-primary]`
    level. Without that, a light header makes every link invisible.

## Layout

Sections are organised by **what the reader is doing**, not by which module
implements the feature:

| Nav group | Holds |
|---|---|
| Getting started | Quick start, Installation, Models, Examples — read once, roughly in order |
| Usage | What you do on an ordinary day: CLI, settings file, MD, ASE, evaluation |
| Advanced | Optional specialist capabilities, each independent |
| Training | Adapting the model |
| Reference | Lookup, not reading |
| Project | Contributing, How to cite |

Every page belongs to a group. `Home` is the only ungrouped entry, because it is
the root — with `navigation.sections`, a loose top-level page renders as a
floating link between the grouped blocks and reads as an unexplained gap.

The settings file lives under **Usage**, not Reference: it is not an optional
deep-dive but the recommended way to drive any long run, and `usage/cli.md`
defers to it for every flag with no command-line form.

```
mkdocs.yml              site config and nav
requirements.txt        pinned mkdocs-material
swap-style.sh           activate a style variant
scripts/                docs CI checks (snippets, anchors)
styles-preview/         style variants (not published)
docs/
  index.md              landing page
  quickstart.md
  installation.md
  models.md
  usage/                cli, settings, md, ase, evaluation
  advanced/             electrostatics, enhanced-sampling, observables,
                        derivatives, binding-energies, integrations
  training/             finetuning, from-scratch
  reference/            api, datasets, changelog, faq
  examples.md
  contributing.md
  cite.md
  assets/               logo.png (wordmark), logo-mark.png (header/favicon)
  stylesheets/extra.css generated — edit styles-preview/ instead
```

`advanced/integrations.md` is the merged home of the former `usage/jax-md.md`
and `usage/potential.md`. Those covered ways of driving SO3LR that the CLI
already does for you, so they moved out of Usage and into one page framed as
"you probably don't need this".

## Editing

Pages are plain Markdown. Adding a page means creating the file **and** adding
it to `nav:` in `mkdocs.yml` — `--strict` will catch a file that exists but is
unreferenced only if something links to it, so keep the nav in sync by hand.

Material-specific syntax used here: admonitions (`!!! note`), collapsible blocks
(`??? question`), and content tabs (`=== "Tab"`). Everything else is standard
Markdown, which keeps a future port to another generator mechanical.

### Keeping reference tables accurate

Several pages mirror what the code actually accepts:

| Page | Mirrors |
|---|---|
| `usage/cli.md` | `click` options in `so3lr/cli/so3lr_cli.py` |
| `usage/settings.md` | `YAML_DEFAULTS`, `KNOWN_YAML_KEYS_EXTRA`, `YAML_KEY_ALIASES` |
| `advanced/observables.md` | `OBSERVABLES` in `so3lr/cli/so3lr_eval.py` and the `--observable` choices |
| `models.md` | `so3lr/model_registry.py` |
| `advanced/enhanced-sampling.md` | `process_cv` and `get_pysages_method` in `so3lr/cli/so3lr_pysages_interface.py`, `parse_cylinder_settings` in `so3lr/cli/so3lr_md.py`, and the enhanced-sampling rules in `so3lr/flash/check.py` |
| `training/from-scratch.md`, `training/finetuning.md` | `so3lr/config/*.yaml` and `run_training` / `run_fine_tuning` in `from_config.py` — these are **separate** loops and honour different keys |

When those change in the code, update the matching table here.
